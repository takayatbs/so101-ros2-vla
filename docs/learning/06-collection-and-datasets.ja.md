# 6. 作業記録から学習データを作る

[教材の入口](../learning_path.ja.md) ／ [前の教材](05-cameras-and-time.ja.md)

同じ「消しゴムを箱へ入れる」作業でも、記録の終わりに片付けを含めるかで、モデルへ与える正解は変わります。箱へ入れた後に元の位置へ手を戻す動作まで混ざると、作業を終えるべき場面と戻るべき場面の区別も学習させることになります。何を1回の作業と数えるかを決めてから収集します。

## 成功条件と開始条件を決める

最初は物体と箱の範囲、開始姿勢、成功条件をそろえます。例えば「物体が箱の中に入り、グリッパーを開いて安定したら成功」という条件です。物体をつかめた時点で成功にする記録と、箱へ置くまで続ける記録を同じラベルで混ぜないようにします。

条件をそろえると、記録と学習の流れを調べやすくなります。ただし、まったく同じ配置だけで集めれば、少しの位置ずれにも対応できるとは限りません。最初の一周を確認した後、想定する配置・照明・物体の違いを計画して追加します。

検証用には学習に入れていない独立した作業を残します。同じ1回の動作から隣り合う画像をランダムに分けると、学習側と検証側にほぼ同じ場面が入り、未知の作業へどれだけ対応したかを判断しにくくなります。

## collect.shの各段階

収集スクリプトはIDLEで準備し、Enter後にTELEOPへ切り替え、練習、記録、配置を戻す時間を繰り返します。練習と配置戻しの間も映像や操作は続きますが、作業Episodeの記録とは分けます。

RECORDING中の保存・やり直し・失敗のキーは、収集を動かしている端末へ入力します。Foxgloveへフォーカスしたままでは、同じ矢印キーを押しても収集操作へ届きません。画面を見る場所と操作を入力する場所を分けて確認します。

既定では、記録時間が満了すると成功として保存します。これは画像から成功を判定した結果ではありません。失敗した作業は、失敗またはやり直しの操作で明示します。時間制限まで操作したという事実だけを、タスク成功の根拠にしないためです。

途中でやり直した記録も、元MCAPは残ります。Sessionには採用Episodeの一覧を保存し、`collection.json` の除外指定で学習対象から外します。保存済みの原記録の成否を後から書き換えることと、学習へ採用するかを選ぶことを区別しています。

## 記録する指令を選ぶ

同じ時刻に見える指令でも、処理の段階によって意味が異なります。

| Topic | 指令の意味 |
|---|---|
| `/teleop/action` | Leaderから計算した要求 |
| `/policy/action` | モデルが出した要求 |
| `/selected_action` | 現在のモードで選んだ要求 |
| `/safe_action` | Safetyを通過した指令 |
| `/follower/applied_action` | Driverが送信に成功した目標 |
| `/hardware/follower/state` | サーボから読み取った実測状態 |

現在の学習用actionには `/follower/applied_action` を使います。手の入力がそのまま実機へ届くとは限らず、選択・変換・制限・通信の処理を通るためです。ただし、送信に成功した目標も機械的に到達した姿勢ではありません。到達は実測状態で確認します。

速度や力を使いたい場合は、取得できている量も確認します。現在のConverterは、欠けた速度を近い時刻の位置差から計算する場合があり、由来を記録します。差分で求めた速度は直接の速度計測とは異なり、ノイズや時刻のずれの影響を受けます。トルクを推測で補わず、effortは有効性の印がある値だけを扱います。現在のモデル入力は関節位置で、これらを自動で追加学習する仕様ではありません。

## rosbagへ一緒に記録しても同期は必要

画像、状態、指令は、それぞれ異なる時刻に届きます。MCAPへ一緒に入れれば同じ作業のデータを保持できますが、同じ配列番号が同じ時刻を表すわけではありません。Converterは元timestampから共通の時間軸を作ります。

共通開始時刻は使うTopicの開始時刻のうち最も遅いものです。共通終了時刻は終了時刻のうち最も早いものです。この重なる範囲へ、DatasetのFPSに従う等間隔のtarget timeを置きます。30 Hzなら約33.3 ms間隔です。

現在の既定は画像・状態・送信済み指令について、target time以前の最新値を選ぶ直前値保持です。後の時刻の情報を先取りせず、その時点までに得た観測と指令を対応付けます。

例えば説明用に、target timeを10.000秒とします。画像が9.990秒、関節状態が9.995秒なら、この時刻までに得た値として選べます。画像の時刻差は−10 ms、状態は−5 msです。10.010秒の画像は近くても未来なので、直前値方式では選びません。

最近傍画像を使う設定もありますが、その場合は未来画像を選ぶ可能性と許容差を明示します。画像とactionの時刻をずらす `action_offset_s` も、全Datasetで同じ意味を保つ必要があります。現在の既定は0秒です。

## 時刻のずれと欠損を残す

既定では20 msを超える時刻差を警告し、50 msを超える対応を除外する設定です。カメラ間のずれ、指令の古さも別に検査します。これらは同期で選んだデータの差に対する条件で、露光そのものの同期精度を測った値ではありません。

使用できない行は `valid=false` として残します。欠損の前後を詰めると、本来の時間間隔が変わり、連続して実行した指令のように見えてしまうからです。学習用の動作列も無効な行をまたがないように読み込みます。

画像が15 FPSで、Datasetを30 Hzへ並べると、同じ画像を複数のtarget timeへ使う場合があります。行数が30 Hz相当になっても、異なる撮影画像が毎秒30枚ある証拠にはなりません。元の画像枚数、間隔、再利用率を `sync_report.json` などで確認します。

整数nsは元時刻を保持する表現です。1 nsという細かい単位で保存することと、測定が1 nsの精度を持つことは異なります。古い形式で秒の小数だけが残っている記録について、変換後に元々なかった時刻精度を取り戻せるわけではありません。

## Native DatasetとLeRobotDataset

元MCAPは再処理できる原記録です。Native Dataset v2はMP4とNPZの対応表として、元画像、target time、状態、指令、時刻差、無効行などを扱います。レビュー用のHTMLも、映像と数値の対応を人が確認するために使います。

LeRobotDataset v3.0では、状態やactionをParquet、画像を等間隔のMP4へ書き出します。元の取得時刻は追加のint64列へ残し、元Episodeとの対応は `so101_bridge.json` に保持します。今回の書き出し形式はローカルのLeRobot本体でも読み込む確認を行っています。

LeRobot形式では無効区間の前後を別Episodeへ分けます。学習と検証を分けるときは、この分割後のEpisode番号だけでなく元の作業IDを使います。同じ作業の断片が両側へ散らばるのを防ぐためです。

| 段階 | 残す理由 |
|---|---|
| 元MCAPと収集時の設定 | 同期・前処理を見直し、事象を調べ直す |
| Native Datasetとレビュー | どの画像・状態・指令を学習へ使うか確認する |
| LeRobotDataset | 対応する学習経路や外部ツールへ渡す |
| 学習ログ・モデル・正規化統計 | 入力と予測の意味を再現する |

変換後の容量だけを見て元データを捨てると、条件を変えて作り直す余地が減ります。保存期間や複製を決めるときは、必要な再現性と利用可能な容量を合わせて考えます。

## 教材として使える記録か確認する

完了した記録の `status: complete` は記録を正常に閉じた状態です。`success: true` は作業成否のラベルです。さらに、`accepted_episodes` は今回の学習へ採用した記録の選択です。この3つは別の判断になります。

変換後は映像と関節・actionを並べ、つかむ瞬間、持ち上げる瞬間、離す瞬間が対応しているかを確認します。時刻が単調に増えること、欠損が隠れていないこと、未来情報を使う意図がない場所で先取りしていないことも確認します。きれいな映像と多いフレーム数だけでは、適切な教師データかは分かりません。

実際の操作は[収集](../collection_script.ja.md)と[Dataset作成](../guide/dataset.ja.md)、時刻の選択は[synchronization.py](../../ros2_ws/src/so101_core/so101_core/synchronization.py)の `aligned_samples`、LeRobot書き出しは[lerobot_io.py](../../ros2_ws/src/so101_core/so101_core/lerobot_io.py)で確認できます。
