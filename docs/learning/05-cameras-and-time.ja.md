# 5. 画像と時間と保存容量

[教材の入口](../learning_path.ja.md) ／ [前の教材](04-configuration-and-runtime.ja.md)

映像が滑らかに見えていても、その画像がいつ撮られ、何枚届き、どの関節状態と組になるかは画面だけでは分かりません。画像の大きさ、圧縮、取得時刻、Queueの待ち時間を分けて調べると、画質・容量・遅延の調整が具体的になります。

## 解像度とFPSが増やすデータ量

640×480のRGB画像を1画素3バイトで表すと、1枚は921,600バイトです。30 FPSなら1台あたり毎秒約27.6 MB、3台で約82.9 MBになります。これは画像の画素だけの計算で、ROSメッセージや記録の管理情報は含みません。

同じ条件で1920×1080にすると、画素数は640×480の6.75倍です。画像を取得した後の色変換、コピー、通信、保存へ渡す量も増えます。カメラ自体が30 FPSを扱えても、USB構成や後段の処理が追いつかなければ、保存できるFPSは下がります。

撮影解像度は機器に要求する画像サイズ、モデル入力サイズは前処理後の大きさです。細かい指先の接触が必要な作業と、大きな箱へ移す作業では必要な情報が異なります。小さくした結果、判断に必要な物体が数画素しかなくなっていないかも映像で確認します。

## USBからAIまでの画像処理

現在のカメラ設定はUSB側の画像形式にMJPGを要求します。取得した画像をOpenCVで展開し、BGRからRGBへ変換した後、記録・表示用のH.264と、必要な場合のモデル入力へ分けます。

```text
USBカメラのMJPG
  → OpenCVで展開・RGBへ変換
    ├→ NVENCでH.264 → RecorderとFoxgloveへ共有
    └→ RGB画像 → 共通前処理 → Policy
```

NVENCはNVIDIAのハードウェア動画エンコーダーです。ここで担当するのはH.264への圧縮です。カメラの撮影、USB受信、MJPGの展開、RGB変換、ROSメッセージの生成まで、すべてがこの専用回路へ移る構成ではありません。

各カメラで圧縮したストリームを記録とFoxgloveへ配るため、表示用に同じ映像をもう一度圧縮する必要はありません。AIには圧縮前のRGBを渡せるので、推論のためだけにH.264を展開し直す往復も避けられます。Raw画像は必要なSubscriberがいるときに配信します。

## 画質と圧縮待ち時間の設定

現在のH.264設定は `qp: 18`、`gop: 15` です。QPは圧縮の量子化の強さに関わり、一般に小さくすると画質を保ちやすい一方、映像の容量は増えます。GOPは基準となるフレームを挿入する間隔に関わります。30 FPSで15フレームなら約0.5秒分で、記録開始や途中からの復元を考える際の条件になります。

エンコーダーでは低遅延の設定と、Bフレームを使わない設定を選んでいます。画像の並べ替え待ちを避けるためです。圧縮率だけを上げる変更では、出力までの待ち時間や途中から復元できる条件も変わる場合があります。画像の品質、容量、圧縮時間を一緒に測ります。

## バッファが大きいと遅延する理由

バッファは処理を待つデータを一時的に置く場所です。撮影が毎秒30枚、圧縮が毎秒20枚なら、全画像を待ち行列へ入れる構成では、毎秒10枚ずつ未処理分が増えます。表示できていても、実物より遅れた映像になっていきます。

一方で、バッファを小さくしすぎると、機器が次の画像を入れる場所を確保できず、取得効率が落ちる場合もあります。今回のOpenCV/V4L2取得ではバッファを2枚に設定しています。これはこの取得経路で使う値で、別のカメラやDriverへそのまま適用できる最適値ではありません。

取得後のNVENC処理では待ち画像を1枚に制限します。新しい画像が来ると、まだ圧縮していない古い待ち画像を置き換える場合があります。すでに圧縮したH.264の参照関係を途中で切らないため、圧縮前と圧縮後の扱いを分けています。

この設計は遅延の蓄積を抑えますが、すべての撮影画像を保存する保証にはなりません。`video_dropped_before_encode` や実際の保存枚数を確認し、欠落を隠さず記録します。

## timestampが表す時点

時刻は、何が起きた時点かを決めて付けます。同じ画像に複数の時刻があっても不自然ではありません。

| 時点 | 意味 | 遅れる要因の例 |
|---|---|---|
| 露光・センサー取得 | 機器が対象を観測した時点 | 露光時間、読み出し |
| ホストでの取得 | PC側で画像を受け取った時点 | USB転送、機器のバッファ |
| メッセージ生成 | ROSメッセージを作った時点 | 展開、色変換、処理待ち |
| Recorderの受信 | 記録Nodeへ届いた時点 | ROS転送、Callback待ち |
| 書き込み呼び出し | Writerへ渡した時点 | 記録処理の待ち |

現在のUSB画像のstampは、OpenCVの `grab()` が成功した直後、展開処理の前に取得したホストのROS時刻です。カメラが露光した時刻そのものは取得していません。したがって、20 msの同期許容差を満たしても、物理的な撮影時刻が20 ms以内に一致した証明にはなりません。

また、Writerへ渡した時刻と、記憶装置への書き込みが物理的に完了した時刻も同一ではありません。学習の同期では保存順やファイル更新時刻の代わりに、メッセージに付いた取得・計測・指令の時刻を使います。

## ROS時刻と経過時間の測定

異なるデータを同じ時間軸へ対応付けるには、比較できる時刻源が必要です。同じPCのROS時刻を使う構成と、複数PCでそれぞれの時計を使う構成では、前提が変わります。複数PCへ広げる場合はNTPやPTPなどの同期方法と、許容するずれを決めます。

Watchdogや処理時間の測定には、`time.monotonic()` のような経過時間用の時計を使います。PCの日時が補正されても、経過時間の判定を逆戻りさせないためです。別PCのmonotonic値同士は、共通の原点として比較できません。

シミュレーションでは `/clock` と `use_sim_time` を使う構成もあります。ただし、このRuntime全体が任意のシミュレーション時計へ対応済みという意味ではありません。ROSのメッセージ時刻と経過時間の監視をどう扱うか、再生・停止・時刻の巻き戻しまで含めて検証します。

## 複数カメラの同期

同じPCへつないだ3台のカメラでも、露光の開始が同時になるとは限りません。ソフトウェアでは近い時刻の画像を選べますが、取得そのものを同時にするには、対応する機器のハードウェアトリガなどを検討します。

現在は、完全に同じtimestampの画像が届くことを前提にしません。ExactTimeはstampの完全一致を求めるため、一致が保証されないデータでは多くの組が作れなくなる可能性があります。保存した時刻の差を評価し、許容外の行を学習から外す方針を使います。

`hardware_synchronized` は実機の同期方法を宣言する設定です。trueへ変更するだけでカメラへトリガ信号が送られる機能ではありません。機器側で得たtimestampを使う場合も、ホスト時刻との対応、単位、時計のずれを記録してから同じ時間軸で比較します。

## 記録・変換・表示で圧縮を共有する範囲

収集とFoxgloveは、同じH.264を使います。Native Datasetへ変換するときも、元がこのH.264なら、再圧縮せずMP4へ格納します。容器の形式を変える処理であり、もう一度画質を落として圧縮する処理とは区別します。

LeRobotDataset v3.0へ書き出す工程では、同期で選んだ画像を等間隔に並べ、前処理も適用するため、オフラインの再エンコードが1回増えます。元MCAPと中間Datasetを残すことで、後から別の同期や前処理を選び直せます。

Foxgloveでは `actual_fps`、画像の経過時間、圧縮前の欠落数、圧縮エラーを読み分けます。GPU使用率が低いことだけで、NVENCが使われていないとも判断できません。カメラ診断の `video_codec` が `h264_nvenc`、圧縮枚数が増加し、エラーが空であることを確認します。

画像取得は[camera.py](../../ros2_ws/src/so101_hardware/so101_hardware/camera.py)、圧縮と待ち画像の扱いは[video.py](../../ros2_ws/src/so101_core/so101_core/video.py)、時刻情報とファイル構造は[データ保管の参考資料](../data_storage_video.ja.md)にあります。
