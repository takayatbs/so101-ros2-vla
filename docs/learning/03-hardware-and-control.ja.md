# 3. 実機の位置と制御と停止

[教材の入口](../learning_path.ja.md) ／ [前の教材](02-ros-communication.ja.md)

関節の数値が取れても、それだけでは動作を始められません。どの関節の値か、単位と原点は何か、正方向はどちらかをそろえる必要があります。例えばdegreeの値をradとして渡すと、同じ数値でも大きく異なる回転を要求します。

## 関節名と単位を機器の数値へ対応付ける

SO-101のサーボは内部レジスターの数値で位置を扱います。ROS側では回転関節をradで表し、Driverが校正情報を使ってサーボの値と変換します。別の機体に直動関節がある場合は、通常はmで表すなど、関節の種類と単位を対応させます。

配列の順も仕様です。`JointState` は名前と位置の配列を持ちますが、モデルの入力やControllerへ渡す数値列には、あらかじめ決めた関節順があります。名前から並べ直す箇所と、順序をそのまま使う箇所を確認します。関節を1つ増やしただけでも、URDF、Controller、Driver、Dataset、モデルの次元に影響します。

現在のグリッパーは開閉を校正した範囲へ対応付けたrad表現を使います。これは把持力や指先間距離の測定値ではありません。別のグリッパーを接続するときは、開度%、距離、角度、力のどれを指令と観測にするかを先に決めます。

## サーボの校正とカメラの校正

アームの校正はエンコーダの値と関節の基準・範囲を対応付ける作業です。今回の `calibration_matches` は、保存したJSONとサーボ内部の校正が一致するかを表します。一致しても、USBの割当が実物と逆なら別のアームの値を読んでしまいます。通信先、校正値、実物の姿勢を組にして確認します。

カメラの校正にはレンズの歪みなどを求める内部パラメーターの校正と、ロボットに対するカメラの位置・向きを求める外部パラメーターの校正があります。アームの校正JSONを使っても、カメラの位置関係は求まりません。

今回の画像条件付きモデルは固定したカメラ配置で作業の映像を学習します。画像内の座標から3次元の把持点を計算する構成へ広げる場合は、カメラ内部・外部パラメーター、ロボットの形状、座標変換を別にそろえます。

## 目標を送る処理とモーター内部の制御

位置制御では目標位置、速度制御では目標速度、トルク制御では目標トルクを与えます。どの値を受け付けるかは駆動装置とDriverの仕様です。位置制御サーボへ位置を送る今回の構成では、モーターを駆動して目標へ近づける処理はサーボ内部が担います。

PIDは目標と実測の差から駆動量を求める制御の一種です。Pは現在の誤差、Iは誤差の蓄積、Dは誤差の変化に対応します。ただし、サーボのレジスターに設定する係数の数値や単位は製品固有です。`position_p_coefficient: 16` を別のモーターへそのまま設定しても、同じ応答になるとは限りません。

物体を挟んでいるときは、グリッパーの実測開度が閉じ目標へ到達しないことがあります。位置の誤差が残っているからといって、さらに閉じ目標を増やせば適切な力になるとは言えません。位置指令、電流・負荷の指標、保護状態、映像上の接触を分けて観察します。この機体はLeaderへ接触の反発力を返す構成ではありません。

## ros2_controlのread・update・write

`ros2_control` は、状態を読む処理、Controllerが目標を扱う処理、駆動側へ書く処理を分ける枠組みです。Hardware Interfaceが公開するstate interfaceとcommand interfaceは、例えば「位置を読める」「位置を指令できる」という機器側の接続仕様です。[公式のHardware Interface説明](https://control.ros.org/jazzy/doc/ros2_control/hardware_interface/doc/hardware_interface_types_userdoc.html)にも定義があります。

今回のC++ Hardware Interfaceは、Python Driverが測った位置をTopicから受け取り、Controllerからの位置指令を別のTopicへ公開します。サーボ通信そのものはPython Driverが担当します。`ros2_control` のread/writeがそのままUSBのread/writeを行う構成ではありません。

| 層 | 現在の処理 | 調べるべき異常 |
|---|---|---|
| Python Driver | サーボの読み取りと目標送信 | 応答なし、通信遅延、アラーム |
| C++ Hardware Interface | 状態・指令の受け渡し | 状態更新停止、Enableや指令の期限切れ |
| Controller | 位置目標をHardware Interfaceへ渡す | interfaceや関節名の不一致、非active |
| Safety | 指令元の選択と値・時刻の検査 | 古い状態、古い指令、制御処理の遅延 |

この分担は、状態を測った時刻とControllerが値を読み出した時刻を区別する理由にもなります。学習用には実測Topicと送信成功後の指令を記録し、Controllerが同じ値を再公開した時刻だけに頼らないようにしています。

## 現在のLeRobot Profileで有効な処理

`config/hardware/robot.yaml` の `control_profile: lerobot` では`joint_state_broadcaster` と `forward_position_controller` を起動します。後者は位置目標を渡すControllerです。旧 `bounded` Profileでは代わりに `joint_trajectory_controller` を使います。

標準のLeRobot Profileは、回転関節へ独自の位置・速度・加速度フィルターを追加しません。`config/hardware/robot.yaml` にある関節範囲の数値はこのProfileでは主に表示・URDF用の情報です。グリッパーには校正範囲への変換があり、`max_relative_target` を設定した場合はDriver側で現在位置との目標差を制限します。既定値のnullはこの追加制限を使わない指定です。

一方、指令の次元・有限値・名前・時刻の検査や通信のWatchdogは残ります。`limits.velocity` を小さくしただけで、このProfileのアームがゆっくり動くと判断しないようにします。実際にどの関数が設定を読むかを確認します。

## 周期と期限の決め方

60 Hzの処理間隔は約16.7 msです。通信と計算がその時間内に終わるかを測り、平均に加えて遅い回の値も確認します。1回だけの長い待ちでも、状態の期限やControllerの処理に影響するためです。

Watchdogは、一定時間更新が途絶えたら停止扱いにする監視です。今回の指令・状態の期限は設定例で0.25秒ですが、これは別の機体にも適切な値という意味ではありません。機体の速度、停止までの距離、通信の遅延をもとに検討します。期限を長くすると停止を避けやすくなる一方、異常後に過去の指令が有効な時間も延びます。

ソフトウェアのタイマー周期と、サーボ内部の制御周期と、AIの観測・推論周期は別です。AIが次の動作列を考えている間も、状態監視と既存の動作列の実行を継続できる構成にします。

## 停止後に何が起きるか

IDLEは待機、TELEOPは人の指令、AUTONOMOUSはモデルの指令を選ぶモードです。FAULTとESTOPは停止状態を保持します。ResetでIDLEへ戻しても動作は自動で再開せず、再び指令元を選びます。

標準のSO-101設定はIDLEや停止でトルクをOFFにする構成です。トルクOFFはアームをその場で支える力もなくなることを意味します。別のロボットで重いアームやブレーキを扱う場合は、制御された減速、姿勢保持、ブレーキ、電源遮断の順序を機構と駆動装置に合わせて決めます。

ROSの停止通知は、通信が途絶えた機器へ届かない可能性があります。物理的な電源遮断とSoftware E-stopの役割は、それぞれ実物で確認します。ROSが提供する通信機能だけで、機体に必要な停止性能が決まることはありません。

## 数値と実物の対応を確かめる

1関節をゆっくり動かしたとき、関節名、位置の増減、物理的な正方向を対応付けます。目標を止めた後に実測がどう変わるかも観察すれば、送信成功と到達の違いを確認できます。最初は[実機を使わない1関節教材](../custom_robot.ja.md)で、指令・状態・タイムアウトを分けて読む練習ができます。

実機の操作は[校正](../calibration.ja.md)と[受入](../hardware_acceptance.ja.md)、Profileの分岐は[control.py](../../ros2_ws/src/so101_core/so101_core/control.py)と[RuntimeのLaunch](../../ros2_ws/src/so101_bringup/launch/runtime.launch.py)を参照します。
