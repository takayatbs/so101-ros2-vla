# 9. 別のロボットへ移植する

[教材の入口](../learning_path.ja.md) ／ [前の教材](08-deployment-and-diagnostics.ja.md)

SO-101で動いた構成から別の機体へ移るとき、再利用しやすいのは観測・指令・停止・記録を分ける考え方です。実機の通信、校正、関節の数、指令方式は機体ごとに確かめます。名前を置き換える前に、新しい機体で同じデータが何を意味するかを定義します。

## 機体の仕様をソフトウェアの入力にする

関節ごとの仕様表には名前、回転か直動か、単位、正方向、原点、取得できる状態、受け付ける指令を書きます。動作範囲、速度・加速度、許容する負荷、必要な通信周期、異常時の停止も、機器の仕様と用途から決めます。

例えば直動グリッパーの開き幅をmで扱うなら、今回のSO-101のrad表現をそのまま使うと単位が変わります。両方が1つの数値だからといって互換にはなりません。Datasetの特徴名やモデルの正規化も、新しい意味に合わせて作ります。

| 決める項目 | 記入する内容 | 対応させる実装 |
|---|---|---|
| 関節と構造 | 名前、個数、種類、親子関係 | URDF、Controller、配列順 |
| 数値の意味 | 単位、符号、原点、開度や力の表現 | Driver、校正、Dataset |
| 指令方式 | 位置・速度・トルク、更新方法、期限 | Controller、Safety、通信 |
| 状態取得 | 測れる項目、周期、時刻、欠損時の表現 | Observation、診断、記録 |
| 機器の能力 | 動作範囲、速度、負荷、電源、保護 | 制限、運用条件、停止 |
| 通信 | バス、ID、応答時間、再試行の上限 | Driver、Watchdog |
| 停止 | PC停止・通信断・電源断での機械的な状態 | 駆動装置、ブレーキ、停止回路 |
| 検証条件 | 試行範囲、合格条件、記録する指標 | 試験と受入記録 |

通信仕様書に位置指令の単位があることと、組み立てた関節の正方向が確認できたことも別です。最初は状態だけを読み、実際の姿勢と数値を対応付けます。再起動後に原点が再現するかも、作業を繰り返すための条件になります。

## DriverとControllerの置き方を選ぶ

既存のメーカーDriverを使える場合でも、指令の更新方式、状態のtimestamp、通信異常時の動作、停止APIを確認します。軌道を1回渡すAPIと、数十Hzで目標を更新するAPIでは、同じCallbackから呼び出すだけでは動き方が一致しません。

通信と制御をどこで行うかは、必要な周期と機器の仕様で選びます。

| 構成 | 検討しやすい条件 | 測定・確認するもの |
|---|---|---|
| Hardware Interfaceから直接通信 | 必要周期内に機器を読めるDriverがある | read/writeの最大時間と失敗時の上限 |
| 外部DriverへTopicで接続 | 別プロセス・別言語・既存Driverを使う | Queue、QoS、時刻、プロセス停止 |
| マイコンで制御しROSから目標を渡す | PC通信と局所制御を分ける | マイコン側の周期、Watchdog、状態返信 |

トルク制御を自分で行う場合は、観測の遅れや演算周期が応答に直接関わります。USB接続の位置制御サーボと同じ周期や停止処理を、根拠なく採用しません。電流指令がそのまま関節トルクなのか、減速機や摩擦、センサーの校正をどう扱うかも確認します。

## URDFとTFと運動学

URDFはリンクと関節のつながり、寸法、回転軸、原点、制限、必要な慣性などを記述するモデルです。TFは座標系の位置・向きの関係を時間とともに扱うために使います。例えばカメラで見た点をアームの基準座標へ変換するには、カメラとアームの位置関係が必要です。[TFの公式説明](https://github.com/ros2/ros2_documentation/blob/jazzy/source/Concepts/Intermediate/About-Tf2.rst)で、時刻を伴う座標変換の意味を確認できます。

関節位置から先端の位置・向きを求める計算が順運動学、先端の目標から関節位置を求める計算が逆運動学です。LeaderとFollowerの関節構造が同じなら関節ごとの対応を使えますが、構造が異なる場合は、先端位置を介した変換などを検討します。

逆運動学で目標に対応する関節角が求まっても、そこまでの途中経路が物体や機体へ接触しないとは限りません。関節制限、自己干渉、作業環境、特異姿勢、到達できない目標を扱う処理が別に必要です。現在のプロジェクトのMoveIt入口には、Planner・IK・実機の衝突回避まで含めた実装はありません。

SO-101のURDFとMuJoCoモデルは近似です。実機の精密な位置計算や接触シミュレーションへ使う場合は、実寸と質量・慣性、衝突形状、センサー位置を確認してモデルを作ります。RVizに形が出ることは、物理モデルの精度の確認とは別です。

## 替える場所をデータの流れで探す

| 対象 | 新しい機体で見直すこと |
|---|---|
| `so101_hardware` | 通信プロトコル、単位変換、状態と指令、停止 |
| `so101_description` | 関節構造、座標系、実寸、制限 |
| `config/hardware/controllers.yaml` | 関節名、interface、Controller、周期 |
| `so101_teleop` | 操作入力の意味と機体への対応 |
| `so101_safety` と共通制御 | 必要な検査、許容値、モード、停止処理 |
| カメラとObservation | センサーの取得、校正、時刻、前処理 |
| RecorderとConverter | 記録Topic、型、stateとactionの定義、同期 |
| 学習とPolicy | 特徴、出力次元、単位、正規化、遅延の扱い |
| Launchと運用 | 必須プロセス、起動順、監視、終了、再接続 |

現在のコードには6関節SO-101やグリッパー名などの前提があります。YAMLの関節数だけを変更して移植が完了する構成ではありません。固定の名前・配列長・単位変換・校正方式・モデル形状を検索し、どの前提を置き換えるかを調べます。

```bash
rg -n 'shoulder_pan|elbow_flex|gripper|JOINT_NAMES' ros2_ws/src config tests
```

検索結果には説明やテストも含まれます。すべてを一括置換するのではなく、取得した状態からモデル出力まで、名前と配列の対応を1つずつ追います。

## 実機のない1関節教材で試す

このリポジトリの `examples/ros2/one_joint_demo.py` はUSBへアクセスせず内部の数値を動かす教材です。目標を受け取り、位置を徐々に変え、指令が途絶えたら計算上の位置を保持します。全体Runtimeと区別するため、両端末でDomain 73を指定します。

GUIの端末Aで起動します。使用中のDomainが73なら、別の空いている番号を両端末でそろえて使います。

```bash
cd /workspace
ROS_DOMAIN_ID=73 python examples/ros2/one_joint_demo.py
```

端末Bでは目標0.2 radを10 Hzで配信します。

```bash
ROS_DOMAIN_ID=73 ros2 topic pub /learning/joint_command \
  std_msgs/msg/Float64 '{data: 0.2}' --rate 10
```

別の端末で実測に相当する位置を読みます。

```bash
ROS_DOMAIN_ID=73 ros2 topic echo /learning/joint_states --once \
  --qos-reliability best_effort
```

この教材は30 Hzで更新し、最大0.2 rad/秒で目標へ近づきます。配信を途中で止めると、最後の指令受信から0.5秒を超えた後、内部の位置を保持します。指令Topicが止まっても、状態の配信は続きます。終了時は配信側と教材側をそれぞれCtrl+Cで終了します。

このFloat64指令にはHeaderがないため、生成時刻を検査できません。保持も計算上の処理です。実機では状態の実測、通信異常、指令の時刻、トルクやブレーキが必要で、教材の停止を物理的な停止へそのまま移せるわけではありません。

## 段階ごとに実装の証拠を残す

最初は通信仕様と停止方式を決め、実機なしで状態・指令・欠損を試します。その後、読み取りだけの実機通信、1関節の小さな動作、全関節の手動操作、短い記録、学習、閉ループ評価へ進みます。

各段階で、次へ進む条件を記録します。読み取り段階なら名前・単位・原点・方向、動作段階なら目標と実測の差・遅延・停止、記録段階なら画像・状態・指令の時刻対応です。テストが通る条件だけでなく、欠損やNaN、通信停止時に何が起きるかも調べます。

実験記録には機体の仕様、コードのバージョン、設定、校正、モデル、測定条件、成功と失敗の件数、未確認の条件を残します。平均的には動く構成でも、負荷が高いときや通信が途切れたときに異なる動きをする可能性があります。再現できる記録があれば、その違いを実装へ戻して調べられます。

複数機体へ広げる際は、Namespace、絶対Topic名、Service、TF Frame、記録先を分けます。GPUやUSBの所有、共通Computeロックも見直します。通信名を分けることと、資源の競合をなくすことを一緒の操作として扱わないようにします。

この教材で仕様表を埋め、観測から実機までの構成図を書いたら、機体固有のDriverと停止方式を具体化できます。必要な周期や精度は、使う機器とタスクの資料・測定から決めます。SO-101の数値はその判断を行うための実装例として使います。

実装の練習は[1関節教材と移植の手順](../custom_robot.ja.md)、試験範囲は[実装状況](../implementation_status.ja.md)、モデルと通信の全体像は[構成の参考資料](../architecture.ja.md)へ進めます。
