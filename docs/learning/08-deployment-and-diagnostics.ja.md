# 8. モデルをロボットで実行し検証する

[教材の入口](../learning_path.ja.md) ／ [前の教材](07-models-and-learning.ja.md)

学習済みモデルは重みのファイルだけでロボットを操作できるわけではありません。どの画像と関節位置を入れ、出力をどの単位へ戻し、いつ実行するかをそろえます。さらに、その指令が古くなった場合や計算が遅れた場合の扱いが必要です。

## モデル登録時に保存する情報

モデル登録ではCheckpointと正規化統計に加え、関節順、単位、画像前処理、ロボット設定、校正、同期条件、学習データの由来を保存します。Runtimeは読み込む際に対応を検査します。

例えばグリッパーの校正を変えると、同じ数値の目標が表す開度も変わる場合があります。学習後に原点や関節順を変更したモデルをそのまま使うと、読み込みに成功しても意図した動作になりません。設定の不一致を早く見つける検査には、こうした取り違えを止める役割があります。

一方、カメラの物理的な位置を動かしても、YAMLの内容が同じならhashは変わりません。設定照合に加え、当日の映像と初期配置を確認します。hashで識別できる条件と、実物で確認する条件を分けて残します。

## IDLE中に初回計算を行う

Runtime起動直後はIDLEで、モデルの読み込みと観測の準備を待ちます。必要な画像と状態がそろうと、初回計算を行い、駆動指令へ送らず結果を捨てます。この準備が済んだことを `/policy/ready` で通知します。

初回はGPUの準備などで通常より時間がかかる場合があります。動作を始めてから最初の計算を待つ構成と分けることで、その待ちを起動前に扱えます。readyは計算を始める準備の確認で、モデルの作業能力を判定した値ではありません。

## 推論する観測を選ぶ

カメラ2台と関節状態は同時に届かないため、Policyも時刻を使って観測を組み立てます。現在の実装は画像履歴と状態履歴から、因果的な対応と許容する時刻差、古さを確認します。片方だけが新しい観測へ、もう片方の古い値を無条件で組み合わせる処理にはしません。

通信が止まっても、最後の位置や画像はメモリーや画面に残ります。観測の値が有限であることと、新しく取得できていることは別です。最終受信からの経過時間とメッセージのstampを検査する理由です。

画像の前処理は学習時と共有します。学習ではRGB、実行ではBGRのまま、という違いも入力分布を変えます。画像の幅・高さだけでなく、チャンネル順、画素範囲、Crop、Resize、歪み補正までそろえます。

## 非同期推論で古い結果を使わない

非同期では推論中も既存の動作列を使います。現在のSchedulerは経過時間から実行する位置を決め、すでに時刻が過ぎた先頭動作を繰り返しません。

途中でTELEOPやIDLEへ変更した後に、以前のAUTONOMOUSの推論が終わる場合もあります。結果にはモードの世代を対応付け、古い世代の結果を採用しないようにします。計算の完了順だけで実行可否を決めないためです。

推論の時間予算を超える、既存動作が尽きる、学習した遅延範囲を超える、といった場合は出力を停止します。今回の非同期Policyは失敗を保持し、同じモードのまま初期化し直して指令を出し続けることを避けています。その後、既存の指令Watchdogなどで停止を扱います。

この設計でも、処理が予定どおり動くことを常に保証できるわけではありません。モデル推論だけでなく、画像配信、前処理、GPU共有、ROS転送、Controller、サーボ通信まで、全体として期限を満たすかを測定します。

## 診断で原因を分ける

| 観察する値・状態 | 調べること |
|---|---|
| カメラのFPSが低い | 撮影設定、USB、取得、配信、圧縮前の欠落 |
| Policyの観測が古い | 画像・状態の更新と時刻対応 |
| 推論時間が長い | 入力サイズ、モデル、反復数、GPUやCPUの競合 |
| Controllerがinactive | 起動処理、Hardware Interfaceの状態、状態受信の期限 |
| Follower通信エラー | 電源、ポート、配線、ID、機器のアラーム |
| FAULTが保持される | Safetyの停止理由と回復条件 |

Foxgloveの診断一覧は各機器の最後の状態を並べて見るために使います。1件の `/diagnostics --once` だけでは全ノードの診断を取得できない場合があります。異常行と停止理由のメッセージを読み、どの検査が失敗したかを特定します。

標準のHardware Interfaceは位置を扱うため、`JointState` のvelocityやeffortがNaNでも、未提供の項目である場合があります。必要なpositionがNaNの場合や、速度・力を使う実装で必要な項目が欠ける場合とは分けます。未提供の速度を0と置くと、実際に動いていても停止中というデータになってしまいます。

## 周期と遅延を測る

平均の推論時間が制御間隔より短くても、一部の長い処理が停止や欠損を起こす可能性があります。p95は測定値の95%がそれ以下になる値で、遅い側の傾向を見る指標です。最大値、期限超過回数、観測の経過時間、欠落枚数も残します。

`ros2 topic hz` は、そのコマンドのSubscriberから見た受信周期です。Publisher内部の処理周期や、カメラの露光周期と完全に同じ測定ではありません。診断の内部計測、元timestamp、保存結果を合わせて読みます。

## オフラインから実機へ検証を進める

| 段階 | 確認できるもの | その段階だけでは分からないもの |
|---|---|---|
| 単体試験 | 単位変換、名前、期限、同期などの条件分岐 | 実機の動き |
| mockでの統合試験 | ROS接続、記録、モデル入出力、モード切替 | 把持の成功 |
| 実機の読み取りと小さな操作 | 原点、方向、通信、追従、停止 | 学習済み方策の作業成功率 |
| オフライン評価 | 未使用Episodeでの予測誤差 | 自分の誤差が蓄積する閉ループ動作 |
| 実機の閉ループ評価 | 決めた条件での成功・失敗と停止 | 未試験の物体・配置での性能 |

実機評価では試行数、初期配置、成功条件、失敗の分類、モデルID、設定、記録先を残します。成功した場面だけを選んで見れば、どの程度安定してできるかは判断できません。失敗も同じ条件で数え、接触やカメラの死角などの原因を映像と数値から調べます。

新しいモデルを試すときは、まずmockで読み込みと停止を確認し、実機ではIDLEで状態・映像・readyを確認します。AUTONOMOUSへ切り替えた時点からモデルの指令が選ばれます。記録開始はその後になるため、切替直後から記録開始までの動きが現在の操作では保存されないことも、評価手順へ含めます。

実行時の観測と世代管理は[Policy Node](../../ros2_ws/src/so101_policy/so101_policy/node.py)、非同期の実行位置は[async_chunks.py](../../ros2_ws/src/so101_core/so101_core/async_chunks.py)、登録情報は[model_registry.py](../../ros2_ws/src/so101_core/so101_core/model_registry.py)で追えます。操作は[手法別のページ](../methods/index.ja.md)を使います。
